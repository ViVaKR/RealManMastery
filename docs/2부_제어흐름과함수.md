## 세션 1 — 분기와 조건 플래그 (45분)

### 핵심 그림: CPU도 "이 조건이 참인가?"를 판단한다

- `cmp` 명령어로 두 값을 비교 → NZCV 플래그(Negative, Zero, Carry, oVerflow) 세팅
- 조건부 분기: `b.eq`, `b.ne`, `b.lt`, `b.gt`, `b.le`, `b.ge`

### 참조 코드 먼저 보여주기 — C# if문

```csharp
// C# — 이걸 먼저 실행해서 결과를 보여줌
int a = 10, b = 20;
if (a < b)
{
    Console.WriteLine("a가 더 작다");
}
else
{
    Console.WriteLine("b가 더 작다");
}
```

> **화면 연출**: dotnet run으로 결과 먼저 시연 → "자 이제 이걸 어셈블리로 만들어보겠습니다."

### 이제 따라 만들기 — ASM

```asm
.data
msg_a: .asciz "a가 더 작다\n"
msg_b: .asciz "b가 더 작다\n"

.global _main
.align 4

_main:
    sub sp, sp, #16
    str x30, [sp]

    mov x0, #10          // a
    mov x1, #20          // b

    cmp x0, x1            // a와 b 비교 -> 플래그 세팅
    b.lt _a_smaller        // a < b 이면 분기

_b_smaller:
    adrp x0, msg_b@PAGE
    add x0, x0, msg_b@PAGEOFF
    bl _printf
    b _done

_a_smaller:
    adrp x0, msg_a@PAGE
    add x0, x0, msg_a@PAGEOFF
    bl _printf

_done:
    ldr x30, [sp]
    add sp, sp, #16
    mov x0, #0
    ret
```

> **대응점 짚기 (반드시 화면에 두 코드 나란히)**: "C#의 `if (a < b)`가 ASM에서는 `cmp` + `b.lt` 두 줄로 쪼개진 겁니다. 고급 언어는 이 두 단계를 하나로 뭉쳐서 보여줄 뿐, 실제로 CPU는 항상 이렇게 '비교 먼저, 판단은 나중'입니다."

### C# for 루프 ↔ ASM 루프

**참조 코드 (C#)**:
```csharp
int sum = 0;
for (int i = 0; i < 5; i++)
{
    sum += i;
}
Console.WriteLine(sum);   // 10
```

**따라 만들기 (ASM)**:
```asm
_main:
    mov x0, #0            // sum = 0
    mov x1, #0            // i = 0

_loop:
    cmp x1, #5             // i < 5 ?
    b.ge _loop_end          // 아니면 탈출

    add x0, x0, x1          // sum += i
    add x1, x1, #1          // i++
    b _loop                 // 다시 루프 처음으로

_loop_end:
    // x0 에 결과(10) 담김
    ...
```

> **강조 포인트**: "`for`문의 초기화-조건-증감 3박자가 ASM에서는 그냥 '레이블 + 조건 분기 + 되돌아가는 b' 조합일 뿐입니다. C#의 for가 마법이 아니라, 이 패턴을 컴파일러가 대신 타이핑해준 것뿐이에요."

## 세션 2 — 함수 호출 규약, 스택 프레임, bl/ret (45분)

### 참조 코드 먼저 — C# 메서드 호출

```csharp
static int Add(int a, int b)
{
    return a + b;
}

static void Main()
{
    int result = Add(7, 35);
    Console.WriteLine(result);   // 42
}
```

> **연결고리 짚기**: "C#에서 `Add(7, 35)` 호출하는 순간, 닷넷 런타임 밑에서는 정확히 오늘 우리가 짜는 이 패턴이 벌어집니다. 파라미터를 레지스터에 담고, `bl`로 뛰고, `ret`로 돌아오고."

### bl과 ret의 실체

```asm
_add:
    add x0, x0, x1     // 파라미터 x0, x1 -> 리턴값 x0
    ret                 // x30(lr)에 저장된 주소로 복귀

_main:
    sub sp, sp, #16
    str x30, [sp]

    mov x0, #7
    mov x1, #35
    bl _add             // x30 <- 다음 명령어 주소 자동 저장, _add로 점프
                          // x0 <- 42 (리턴값)

    ldr x30, [sp]
    add sp, sp, #16
    mov x0, #0
    ret
```

> **핵심 개념**: "`bl`은 그냥 점프가 아닙니다. Branch with Link — 점프하면서 동시에 '돌아올 주소'를 x30(lr)에 저장합니다. `ret`는 그 x30 값으로 되돌아가는 것뿐이고요. C#의 `return`이 하는 일이 바로 이겁니다."

### 스택 프레임 — 함수가 중첩될 때

C#에서는 함수가 함수를 불러도 아무 문제 없이 동작하는데, 그 이유:

```asm
// 함수 A가 함수 B를 부르면, A의 x30(lr)을 스택에 저장해둬야
// B 안에서 또 bl을 쓰더라도 A로 돌아갈 주소가 안전함

_func_a:
    sub sp, sp, #16
    str x30, [sp]        // A의 복귀 주소를 스택에 백업

    bl _func_b             // B 호출 (여기서 x30이 덮어써짐)

    ldr x30, [sp]          // A의 복귀 주소 복원
    add sp, sp, #16
    ret
```

> **강조**: "이 저장/복원 패턴이 바로 '스택 프레임'입니다. C#에서는 이 과정을 눈으로 볼 일이 없지만, 함수가 재귀적으로, 혹은 여러 겹으로 호출될 때 이게 없으면 프로그램은 어디로 돌아가야 할지 완전히 길을 잃습니다."

## 세션 3 — 재귀와 하노이의 탑: 스택 깊이 체감 (60분)

여기가 오늘의 **클라이맥스**입니다. 재귀는 눈으로 안 보이면 절대 이해가 안 되는 개념이라, 스택을 실제로 까서 보여주는 게 핵심입니다.

### 참조 코드 먼저 — C# 하노이의 탑

```csharp
static int moveCount = 0;

static void Hanoi(int n, char from, char to, char via)
{
    if (n == 0) return;
    Hanoi(n - 1, from, via, to);
    moveCount++;
    Console.WriteLine($"{moveCount}: {from} -> {to}");
    Hanoi(n - 1, via, to, from);
}

static void Main()
{
    Hanoi(3, 'A', 'C', 'B');   // 원반 3개, 7번 이동으로 완료
}
```

> **먼저 실행해서 보여주기**: "원반 3개면 7번, 4개면 15번... 이게 왜 재귀 호출로 자연스럽게 풀리는지, 이제 어셈블리로 그 안을 뜯어봅니다."

### 재귀 함수 ASM — 팩토리얼로 먼저 워밍업

복잡한 하노이 전에, 재귀의 뼈대를 팩토리얼로 먼저 익히기:

```asm
// int factorial(int n) { return n <= 1 ? 1 : n * factorial(n-1); }
_factorial:
    sub sp, sp, #16
    str x30, [sp]           // 이번 호출의 복귀 주소 저장
    str x0, [sp, #8]         // 이번 호출의 n 값도 저장 (재귀 중 x0가 덮어써지므로!)

    cmp x0, #1
    b.le _base_case

    sub x0, x0, #1            // n - 1
    bl _factorial               // 재귀 호출
    // 여기 돌아왔을 때 x0 = factorial(n-1)

    ldr x1, [sp, #8]            // 저장해둔 이번 n 값 복원
    mul x0, x0, x1               // n * factorial(n-1)
    b _end

_base_case:
    mov x0, #1

_end:
    ldr x30, [sp]
    add sp, sp, #16
    ret
```

> **여기서 반드시 라이브 시연**: lldb로 `factorial(5)` 호출 중간에 브레이크포인트 걸고 `bt`(backtrace)로 스택이 5단으로 쌓여있는 걸 실제로 보여주기. "이게 재귀입니다. 눈에 안 보이지만 실제로 이만큼 쌓입니다."

```bash
(lldb) b _factorial
(lldb) run
(lldb) bt        # 재귀가 깊어질수록 스택 프레임이 쌓이는 게 눈에 보임
(lldb) frame select 3
(lldb) register read x0
```

### 진짜 겪었던 버그 1: off-by-one

> **실전 회고 멘트**: "저도 처음에 여기서 정확히 이 버그를 겪었습니다. `n <= 1`을 `n < 1`로 잘못 쓰면 어떻게 되는지 보여드릴게요."

```asm
    cmp x0, #1
    b.lt _base_case      // 버그: n < 1 이면, n=1일 때 base case를 안 타고 계속 재귀
```

- n=1일 때 `factorial(0)`을 다시 호출하게 되고, `mov x0, #1` 후에도 다시 `sub x0, x0, #1`이 걸려 n=0에서 또 재귀 → 결국 음수까지 무한히 내려가다 스택 오버플로우로 크래시
- **라이브로 크래시 재현** → lldb로 스택이 비정상적으로 깊어진 걸 `bt`로 보여주기

### 진짜 겪었던 버그 2: 레지스터 폭 불일치

> "1부에서 `w` 레지스터에 쓰면 상위 32비트가 날아간다고 말씀드렸죠? 재귀에서 이게 왜 진짜 무섭냐면..."

```asm
    mul w0, w0, w1     // w 레지스터로 곱셈 (32비트 결과)
    // 이후 x0를 그대로 리턴값으로 사용하면
    // 상위 32비트에 이전 호출에서 남아있던 쓰레기 값이 섞여있을 수 있음
```

- 32비트 연산 결과를 64비트 x 레지스터에 그대로 얹어 쓰면, 상위 비트에 이전 스택 프레임에서 남은 값이 남아있어 **가끔은 맞고 가끔은 틀리는** 재현하기 어려운 버그가 됨
- 이런 종류의 버그가 왜 "재귀에서 특히 무서운지" — 호출 깊이에 따라 증상이 다르게 나타나기 때문

### 하노이의 탑 — 이제 진짜로

팩토리얼로 몸풀기 끝났으니, 3개 파라미터를 가진 하노이를 ASM으로 구현. 여기서는 **완전한 코드를 직접 타이핑하기보다, 팩토리얼 구조를 확장하는 방식**으로 접근 (파라미터가 여러 개일 때 스택에 어떻게 백업하는지가 핵심 포인트).

```asm
// void hanoi(int n, char from, char to, char via)
// x0=n, x1=from, x2=to, x3=via

_hanoi:
    cmp x0, #0
    b.eq _hanoi_end

    sub sp, sp, #48           // n, from, to, via, lr 저장 공간 확보 (16의 배수)
    str x30, [sp]
    str x0, [sp, #8]           // n
    str x1, [sp, #16]          // from
    str x2, [sp, #24]          // to
    str x3, [sp, #32]          // via

    // hanoi(n-1, from, via, to)
    sub x0, x0, #1
    // x1=from 그대로, x2<-via, x3<-to (순서 재배치)
    mov x4, x2
    mov x2, x3
    mov x3, x4
    bl _hanoi

    // moveCount++ 및 출력 (printf 호출, 저장해둔 값들 복원해서 사용)
    ldr x1, [sp, #16]
    ldr x2, [sp, #24]
    // ... printf 호출 부분 생략 (실습에서 직접 채우게 유도)

    // hanoi(n-1, via, to, from) — 두 번째 재귀 호출도 동일 패턴
    ldr x0, [sp, #8]
    sub x0, x0, #1
    ldr x1, [sp, #32]          // via
    ldr x2, [sp, #24]          // to
    ldr x3, [sp, #16]          // from
    bl _hanoi

    ldr x30, [sp]
    add sp, sp, #48

_hanoi_end:
    ret
```

> **핵심 통찰 (여기서 학생들이 "아하" 하는 포인트)**: "재귀 호출 하나마다 파라미터 전부를 스택에 새로 저장해야 하는 이유 — 두 번째 재귀 호출 전에 첫 번째 재귀 호출이 x0~x3을 완전히 다른 값으로 오염시켜놓기 때문입니다. C#에서는 컴파일러가 이걸 자동으로 해주지만, 여기선 우리가 직접 챙겨야 해요."

> **라이브 시연**: n=3으로 실행 → lldb `bt`로 최대 스택 깊이가 3단계까지 쌓이는 것 실제로 확인 → "원반이 4개, 5개였으면 스택이 몇 단까지 쌓였을지" 질문 던지고 답 유도
