# Native AOT를 쓰는 진짜 이유 — "선택"이 아니라 "전제조건"

## 이 강좌가 증명하려는 것

`SapienMastery` 프로젝트의 그림은 단순합니다.

```
ARM64 Assembly (_main)
      │
      │  bl _csharp_sapien_entry
      ▼
SapienCore.dylib  ← C# (Native AOT)
      │
      │  return (w0)
      ▼
ARM64 Assembly (exit code)
```

어셈블리가 `bl` 한 줄로 C# 함수를 부르고, C#은 값을 계산해 레지스터로 돌려준다. 이 그림 자체가 곧 "AOT를 왜 쓰는가"에 대한 가장 정직한 답입니다. 이론으로 설명하기보다, 이 프로젝트가 성립하는 조건을 하나씩 따라가 보면 됩니다.

## 일반 .NET 앱이 이 그림에 낄 수 없는 이유

보통의 .NET 애플리케이션(JIT 기반)이 실행되려면 다음이 전제됩니다.

- **CoreCLR 런타임**이 대상 머신에 설치되어 있거나 함께 배포되어야 함
- 프로그램은 IL(중간 언어) 형태로 존재하고, **실행 시점에 JIT 컴파일러가 기계어로 변환**
- 진입점은 `Main()` 이며, **.NET 런타임이 프로세스의 주인**이 되어 시작을 통제

이 세 가지 전제 중 단 하나도 지금 프로젝트의 조건과 맞지 않습니다. `_main`은 어셈블리 쪽에 있고, 어셈블리는 **.NET이라는 개념 자체를 모릅니다.** 그냥 `bl` 명령으로 어떤 주소의 코드를 부를 뿐이죠. 그 코드가 C#으로 짜였는지, Rust로 짜였는지, 손으로 쓴 어셈블리인지 어셈블리 입장에서는 알 도리가 없고, 알 필요도 없습니다.

## Native AOT가 바꾸는 것

Native AOT는 이 전제를 정확히 뒤집습니다.

| | 일반 .NET (JIT) | Native AOT |
|---|---|---|
| 런타임 설치 필요 여부 | 필요 | **불필요** — 산출물 자체가 완결된 기계어 |
| 실행 단위 | IL + 런타임 | **순수 네이티브 코드** (`.dylib`/`.so`/`.dll`) |
| 프로세스의 주인 | .NET 런타임 (`Main` 진입) | **호출하는 쪽** (어셈블리, C, Rust, Swift 등 무엇이든) |
| 상대방이 알아야 할 것 | ".NET이 뭔지" | **아무것도 몰라도 됨** — C ABI로 노출된 심볼 하나 |

`[UnmanagedCallersOnly(EntryPoint = "csharp_sapien_entry")]`가 하는 일이 바로 이겁니다. C# 메서드를 **C 계약(Calling Convention)을 따르는 평범한 네이티브 함수**로 노출시키는 것. 어셈블리는 이 함수가 C#으로 쓰였다는 사실 자체를 모른 채로, 그냥 `nm`으로 확인 가능한 심볼 하나에 `bl`을 날릴 뿐입니다.

## "최적"이 아니라 "유일한 선택지"인 이유

다른 시나리오(서버리스 콜드스타트, 컨테이너 이미지 크기, CLI 툴 반응성)에서 AOT는 **더 나은 선택지**입니다 — JIT로도 어쨌든 되긴 하니까요. 성능과 비용의 문제입니다.

하지만 지금 시나리오는 다릅니다.

> 상대방(어셈블리, Rust, C/C++, Swift)이 **애초에 .NET 런타임의 존재를 전제할 수 없는 세계**에 있다면, JIT 기반 .NET은 이 그림에 낄 자격 자체가 없습니다.

- Rust의 `cdylib`가 C# 함수를 호출하려 할 때, Rust는 "저 심볼 뒤에 CoreCLR이 떠 있는지"를 신경 쓸 방법이 없습니다. 그냥 C ABI 함수를 기대할 뿐입니다.
- iOS/macOS 앱이 Swift에서 `.dylib`를 링크할 때도 마찬가지입니다. 앱 번들 안에 CoreCLR을 통째로 심어두는 건 비현실적입니다.
- 임베디드/펌웨어급 환경이라면 애초에 런타임을 얹을 메모리·저장공간 여유가 없는 경우도 흔합니다.

즉 이 시나리오에서 "JIT냐 AOT냐"는 트레이드오프의 문제가 아니라, **"성립하느냐 안 하느냐"의 문제**입니다. JIT 기반 .NET을 이 자리에 넣으려는 시도 자체가 애초에 성립하지 않기 때문에, 선택지는 사실상 하나로 좁혀집니다.

## 이 프로젝트가 증명해 보인 것

`CMakeLists.txt`에서 `dylib`를 `SapienApp` 옆으로 복사하고 `@executable_path`로 RPATH를 잡아둔 것, `nm -gU ... | grep csharp_sapien_entry`로 심볼 노출을 눈으로 확인시켜 준 것 — 이 모든 디테일이 결국 같은 이야기를 하고 있습니다.

**C#은 더 이상 ".NET 프로그램"이 아니라, 링커가 이해하는 하나의 부품(component)이 되었다.**

호출하는 쪽이 어셈블리든, 앞으로 다룰 Rust든, C 라이브러리든 — 상대는 그 부품 안에 무슨 언어가 들어있는지 몰라도 되고, 몰라야 정상입니다. Native AOT는 정확히 그 "몰라도 되게 만드는" 기술이고, 그래서 이 시나리오에서는 최적화 옵션이 아니라 **성립 조건**입니다.
