# 디스어셈블리와 디버거 기초 개념
### — "왜 그런가?"를 놓치지 않는 사람들을 위한 노트 —

> 니모닉(mnemonic)을 백날 외워봐야, "왜 이런 구조인가"를 모르면 금방 휘발된다.
> 이 문서는 어셈블리/디버거를 배울 때 대부분의 교재가 "당연하다"고 건너뛰는
> 근본적인 질문들을 짚어본다.

---

## 1. 메모리는 바이트 배열이고, 명령어는 리틀 엔디안으로 해석된다

ARM64에서 모든 명령어는 **4바이트 고정 길이**이며, 메모리에는 **리틀 엔디안**으로 저장된다.

```
(lldb) memory read 0x1000002dc
0x1000002dc: 41 02 80 d2 02 00 01 8b 00 00 80 d2 c0 03 5f d6
```

이걸 4바이트씩 끊어서 **바이트 순서를 뒤집어(리틀 엔디안)** 32비트 워드로 만들면:

| 주소 | 바이트 (파일 순서) | 워드 (LE로 뒤집음) | 명령어 |
|---|---|---|---|
| 0x1000002dc | 41 02 80 d2 | 0xd2800241 | `mov x1, #0x12` |
| 0x1000002e0 | 02 00 01 8b | 0x8b010002 | `add x2, x0, x1` |
| 0x1000002e4 | 00 00 80 d2 | 0xd2800000 | `mov x0, #0x0` |
| 0x1000002e8 | c0 03 5f d6 | 0xd65f03c0 | `ret` |

`disassemble` 결과와 1:1로 대응된다. 즉 어셈블리 명령어란 결국
**"4바이트짜리 숫자를 CPU가 정해진 규칙대로 해석한 결과"**일 뿐이다.

## 2. `disassemble`(lldb) vs `objdump` — 목적은 같고 시점이 다르다

둘 다 궁극적 목적은 동일하다:

> **기계어(0과 1)를 사람이 읽을 수 있는 어셈블리로 되돌리는 것 (= 디스어셈블)**

| | `disassemble` (lldb 내부 명령) | `objdump` (독립 CLI 도구) |
|---|---|---|
| 실행 환경 | 디버거 안, 프로세스를 **실제로 띄운 상태** | 파일 시스템의 **바이너리 파일 자체**를 분석 |
| 시점 | 런타임 중 (브레이크포인트 걸고 현재 위치 확인) | 정적 분석 (실행 없이도 가능) |
| 강점 | 레지스터/메모리 등 **살아있는 컨텍스트**와 함께 확인 | 전체 함수, 심볼 테이블, 섹션 헤더 등 **파일 구조 전체**를 훑음 |

비유: `objdump`는 "책 전체를 미리 번역해서 인쇄한 것", `disassemble`(lldb)은
"지금 읽는 페이지만 그때그때 번역해서 보여주는 것".

실무에서는 보통 `objdump`(또는 macOS의 `otool -tv`)로 전체 구조를 먼저 훑고,
`lldb`의 `disassemble` + `memory read`로 실행 흐름을 실시간으로 파고드는 조합을 쓴다.

## 3. 화살표(`->`)는 PC(Program Counter) — "다음에 실행될" 명령어

```
    0x1000006cc <+12>: mov    x19, #0x25   ← 이미 실행 완료
->  0x1000006d0 <+16>: mov    x20, #0x43   ← 아직 실행 전 (다음 차례)
```

> **PC(화살표)가 가리키는 줄은 "다음에 fetch될 명령어"이며, 아직 실행 전이다.**

CPU는 Fetch → Decode → Execute 사이클로 동작하고, PC는 항상
"이제 곧 fetch할 대상"을 미리 가리킨다. `si`(step instruction) 한 번을 치면
화살표가 한 줄 내려가면서, 방금 그 줄이 실행 완료 상태로 바뀐다.

**확인 방법**: `register read x19 x20` 을 쳐서 아직 실행 안 된 레지스터가
이전 값(또는 쓰레기 값)인지 확인해보면 체감할 수 있다.

## 4. `si`/`ni` vs `step`/`next` — 두 개의 서로 다른 축

VSCode의 F11(Step Into), F10(Step Over)에 익숙하면 헷갈리기 쉬운 부분.
사실 이건 **두 개의 독립적인 축**이 겹쳐서 생기는 개념이다.

**축 1 — 이동 단위**: 명령어(instruction) 단위 vs 소스코드(line) 단위
**축 2 — 함수 호출 시 동작**: 내부로 들어감(Into) vs 건너뜀(Over)

| | 소스 레벨 (source line) | 명령어 레벨 (instruction) |
|---|---|---|
| **Into** (함수 호출 시 내부로 진입) | `step` / `s` | `si` (stepi) |
| **Over** (함수 호출 시 건너뜀) | `next` / `n` | `ni` (nexti) |

즉 `si`도 사실 "Step **Into**"에 해당한다 — 다만 한 걸음의 단위가
"소스 한 줄"이 아니라 "어셈블리 명령어 한 개"일 뿐이다.

### "소스 레벨"이 가능한 이유 — 기적이 아니라 디버그 심볼(DWARF)

소스코드 한 줄이:

```c
int c = a + b;
```

컴파일되면 실제로는 여러 개의 어셈블리 명령어로 쪼개진다:

```
mov x19, #0x25      ; a = 37
mov x20, #0x43       ; b = 67
add x21, x19, x20    ; c = a + b
```

컴파일 시 `-g` 옵션 등으로 **"이 어셈블리 명령어는 소스 몇 번째 줄에 해당하는가"**
매핑 테이블(디버그 정보, 보통 DWARF 포맷)이 함께 생성된다.

`step`/`next`는 이 매핑 테이블을 보고, **소스 한 줄에 해당하는 명령어 뭉치 전체**를
실행한 뒤 다음 소스 줄로 넘어간다. 반면 `si`/`ni`는 이런 정보 없이도
**명령어 자체(기계어)만으로** 한 칸씩 움직일 수 있다.

> `strip`된(디버그 정보가 없는) 바이너리에서 `step`을 치면, 소스 매핑을
> 못 찾아서 사실상 `si`처럼 동작하거나 에러가 난다.

VSCode의 F11(Step Into)은 내부적으로 lldb/gdb의 `step`(소스 레벨)에 해당하는
동작을 예쁜 UI로 감싼 것이다.

## 5. 왜 명령어 자체도 메모리에 저장되는가? — 폰 노이만 구조

```
    0x100000730 <+28>: mov    x19, #0x25 ; =37
    0x100000734 <+32>: mov    x20, #0x43 ; =67
->  0x100000738 <+36>: add    x21, x19, x20
```

여기서 흔히 헷갈리는 지점: **저 주소가 x19 값이 저장되는 곳인가?** → 아니다.

**두 가지를 분리해서 봐야 한다:**

| | 저장 위치 | 저장되는 것 |
|---|---|---|
| 명령어 자체 (`mov x19, #0x25`) | **메모리** (`.text` 섹션) | "x19에 37을 넣어라"는 **명령문(기계어 인코딩)** |
| x19라는 값 (37) | **CPU 레지스터** | 계산에 쓰이는 **실제 데이터** |

### 왜 명령어까지 메모리에 있어야 하나?

**폰 노이만 구조(von Neumann architecture)**의 핵심 통찰:

> **프로그램(명령어)도 결국 데이터다. 그래서 메모리에 저장된다.**

CPU의 Fetch-Decode-Execute 사이클을 보면:

1. **Fetch**: PC가 가리키는 메모리 주소(`0x100000730`)에서 **명령어 자체(기계어)를 읽어옴**
2. **Decode**: 비트 패턴을 해석 — "아, `mov x19, #0x25`구나"
3. **Execute**: 해석한 대로 **레지스터 x19에 37을 씀**

CPU는 "다음에 뭘 해야 하는지" 알기 위해서도 메모리에서 명령어를 읽어와야 한다.
명령어가 메모리에 없으면 CPU는 애초에 뭘 하라는 건지 알 방법이 없다.

### 비유

- **메모리의 코드 영역** = 레시피북 (종이에 적힌 "설탕 두 스푼 넣어라"는 지시사항)
- **레지스터** = 실제로 손에 들고 있는 설탕 그릇 (진짜 재료/값)

레시피 자체도 어딘가(메모리)에 적혀있어야 요리사(CPU)가 읽고 따라할 수 있고,
그 결과물(37이라는 값)은 손에 든 그릇(레지스터)에 담긴다.

### 컴파일 ~ 실행까지의 흐름

컴파일 시점에 이미 다음이 결정된다:

- 각 명령어가 몇 바이트짜리 기계어로 인코딩될지
- 그 명령어들이 파일의 어느 오프셋(실행 시 어느 가상주소)에 배치될지

이 정보가 실행 파일(Mach-O, ELF 등)의 **`.text` 섹션**에 순서대로 저장되고,
프로그램 실행 시 OS 로더가 이 섹션을 프로세스의 가상 메모리 공간에 그대로
매핑(로드)한다 — 그게 지금 lldb에서 보이는 `0x100000730` 같은 주소들이다.

---

## 핵심 한 줄 요약

> **명령어(코드)는 메모리에, 계산 결과(값)는 레지스터에.**
> **PC는 항상 "다음에 실행할 것"을 가리키고, 소스 레벨 스텝은 디버그 심볼(DWARF)의 힘이다.**

이 구조를 이해하고 나면, `mov`, `add`, `stp` 같은 니모닉들이
단순 암기가 아니라 "당연한 절차"로 머리에 남기 시작한다.
