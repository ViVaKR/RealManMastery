# ARM64 예제 코드 — 11주차: 배열과 주소 연산

> 드디어 8주차에서 손으로 풀었던 `sp+16, sp+20, sp+24...`를 **인덱스 하나로 대체**할 시간이네.
> 이번 주 핵심 명제: **"배열 인덱싱은 문법이 아니라 `base + index*size` 주소 계산이다"**, 그리고
> **"포인터 연산은 그냥 정수 덧셈이다"**라는 걸 어셈블리로 직접 확인하는 게 목표일세.

---

## Addressing Mode 총정리 — 먼저 문법부터

| 문법 | 이름 | 의미 |
|---|---|---|
| `[Xn, #imm]` | 즉치 오프셋 | `base + 상수` (지금까지 계속 쓴 `[sp, #16]` 같은 패턴) |
| `[Xn, Xm]` | 레지스터 오프셋 | `base + 레지스터값` |
| `[Xn, Xm, LSL #n]` | **스케일드 오프셋** | `base + (레지스터값 << n)` — 배열 인덱싱의 핵심! |
| `[Xn, Wm, SXTW #n]` | 스케일드+부호확장 | 32비트 인덱스를 64비트로 부호확장하며 스케일 |
| `[Xn, #imm]!` | **Pre-index** | 먼저 `base += imm` 하고 나서 그 주소에 접근 (writeback) |
| `[Xn], #imm` | **Post-index** | 먼저 그 주소에 접근하고 나서 `base += imm` (writeback) |

`int` 배열은 원소 크기가 4바이트라, 인덱스 `i`에 대해 `LSL #2`(= ×4)를 쓰는 게 관용 패턴이네. `long`/`double`이면 `LSL #3`(×8).

## 예제 1 — 8주차 리팩터링: 인덱스 루프로 배열 순회

**C 등가 코드**
```c
extern void go_print_int(int v);

int main(void) {
    int scores[5] = {95, 82, 67, 45, 78};
    int sum = 0;

    for (int i = 0; i < 5; i++) {
        sum += scores[i];        // ← 8주차엔 이걸 5번 손으로 풀어썼었지!
    }

    go_print_int(sum);   // 367
    return 0;
}
```

**ARM64 어셈블리**
```asm
    .text
    .global _main
    .extern _go_print_int

_main:
    stp     x29, x30, [sp, #-48]!    // FP/LR(16) + 배열 5*4=20바이트(정렬위해 32) = 48
    mov     x29, sp

    // 배열 초기화 (여전히 5개는 손으로 넣지만, "순회"는 이제 안 함!)
    mov     w0, #95
    str     w0, [sp, #16]
    mov     w0, #82
    str     w0, [sp, #20]
    mov     w0, #67
    str     w0, [sp, #24]
    mov     w0, #45
    str     w0, [sp, #28]
    mov     w0, #78
    str     w0, [sp, #32]

    add     x21, sp, #16              // ★ 배열의 "시작 주소"를 x21에 보관 (callee-saved)
    mov     w19, #0                    // sum
    mov     w20, #0                    // i

loop_cond:
    cmp     w20, #5
    b.ge    loop_end

    ldr     w0, [x21, w20, sxtw #2]     // ★ scores[i] = *(base + i*4)  ─ 이 한 줄이 핵심!
    add     w19, w19, w0                // sum += scores[i]

    add     w20, w20, #1                // i++
    b       loop_cond

loop_end:
    mov     w0, w19
    bl      _go_print_int                // 367

    mov     w0, #0
    ldp     x29, x30, [sp], #48
    ret
```

**포인트 — 8주차 대비 확 줄어든 코드량**
8주차에서는 학생 3명(!)에도 코드가 60줄에 달했는데, 여기선 **배열 크기가 5든 500이든 루프 몸통(`loop_cond`~`loop_end` 사이)이 절대 안 늘어남**. `LDR w0, [x21, w20, sxtw #2]` 한 줄이 `sp+16`, `sp+20`, `sp+24`... 를 전부 대체한 것이네. 이게 9~10주차(함수)와 함께 배열이 코드 재사용성을 얼마나 끌어올리는지 보여주는 사례일세.

**포인트 — `sxtw #2`가 붙은 이유**
- `w20`(인덱스 `i`)은 32비트인데, 주소 계산은 64비트 레지스터(`x21`)로 해야 함 → `SXTW`로 부호확장
- `int` 원소 크기가 4바이트라 인덱스에 `#2`(=`×4`)만큼 시프트 → 이게 `LSL #2`와 동급이지만, 여기선 확장까지 겸하는 `SXTW #2` 형태로 씀

## 예제 2 — 최댓값 찾기 (CSEL로 분기 없이!)

**C 등가 코드**
```c
extern void go_print_int(int v);

int main(void) {
    int scores[5] = {95, 82, 67, 45, 78};
    int max = scores[0];

    for (int i = 1; i < 5; i++) {
        if (scores[i] > max) max = scores[i];
    }

    go_print_int(max);   // 95
    return 0;
}
```

**ARM64 어셈블리**
```asm
    .text
    .global _main
    .extern _go_print_int

_main:
    stp     x29, x30, [sp, #-48]!
    mov     x29, sp

    mov     w0, #95
    str     w0, [sp, #16]
    mov     w0, #82
    str     w0, [sp, #20]
    mov     w0, #67
    str     w0, [sp, #24]
    mov     w0, #45
    str     w0, [sp, #28]
    mov     w0, #78
    str     w0, [sp, #32]

    add     x21, sp, #16
    ldr     w19, [x21]                 // max = scores[0]
    mov     w20, #1                     // i = 1

loop_cond:
    cmp     w20, #5
    b.ge    loop_end

    ldr     w0, [x21, w20, sxtw #2]      // scores[i]
    cmp     w0, w19                      // scores[i] vs max
    csel    w19, w0, w19, gt             // ★ scores[i] > max 이면 w19=scores[i], 아니면 그대로 (분기 없이!)

    add     w20, w20, #1
    b       loop_cond

loop_end:
    mov     w0, w19
    bl      _go_print_int                 // 95

    mov     w0, #0
    ldp     x29, x30, [sp], #48
    ret
```

**포인트 — 5주차 `CSEL`이 여기서 실전 투입**
`if (scores[i] > max) max = scores[i]`를 `B.cond`로 분기시켜 처리할 수도 있지만, 이렇게 **매 반복 결과가 갈릴 확률이 높은(분기 예측이 어려운) 패턴**에서는 `CSEL`(조건부 선택)로 처리하면 **분기 예측 실패(misprediction) 비용 자체가 없음**. 5주차에서 "분기 없이 조건 처리하는 법"으로 배운 게 여기서 성능 최적화 기법으로 이어지는 셈이네.

## 예제 3 — 2차원 배열 (행 우선 순회, Row-major)

**C 등가 코드**
```c
extern void go_print_int(int v);

int main(void) {
    int matrix[2][3] = {
        {1, 2, 3},
        {4, 5, 6}
    };
    int sum = 0;

    for (int r = 0; r < 2; r++) {
        for (int c = 0; c < 3; c++) {
            sum += matrix[r][c];
        }
    }

    go_print_int(sum);   // 21
    return 0;
}
```

**ARM64 어셈블리**
```asm
    .text
    .global _main
    .extern _go_print_int

_main:
    stp     x29, x30, [sp, #-48]!
    mov     x29, sp

    // matrix[2][3]을 1차원 6칸으로 평탄화해서 저장 (메모리는 원래 1차원이니까!)
    mov     w0, #1
    str     w0, [sp, #16]        // matrix[0][0]
    mov     w0, #2
    str     w0, [sp, #20]        // matrix[0][1]
    mov     w0, #3
    str     w0, [sp, #24]        // matrix[0][2]
    mov     w0, #4
    str     w0, [sp, #28]        // matrix[1][0]
    mov     w0, #5
    str     w0, [sp, #32]        // matrix[1][1]
    mov     w0, #6
    str     w0, [sp, #36]        // matrix[1][2]

    add     x21, sp, #16          // 배열 시작주소
    mov     w19, #0                // sum
    mov     w22, #0                // r

row_loop:
    cmp     w22, #2
    b.ge    row_end

    mov     w20, #0                // c

col_loop:
    cmp     w20, #3
    b.ge    col_end

    // ★ 인덱스 공식: matrix[r][c] = base + (r*COLS + c) * 4   (COLS=3)
    mov     w0, #3
    mul     w1, w22, w0             // r * 3
    add     w1, w1, w20             // + c
    ldr     w0, [x21, w1, sxtw #2]  // *(base + (r*3+c)*4)

    add     w19, w19, w0            // sum += matrix[r][c]

    add     w20, w20, #1            // c++
    b       col_loop

col_end:
    add     w22, w22, #1            // r++
    b       row_loop

row_end:
    mov     w0, w19
    bl      _go_print_int            // 21

    mov     w0, #0
    ldp     x29, x30, [sp], #48
    ret
```

**포인트 — "2차원 배열"이라는 건 사실 착시**
메모리엔 애초에 "2차원"이라는 개념이 없음. `matrix[2][3]`은 실제로 **6칸짜리 1차원 메모리**를 `row * COLS + col` 공식으로 흉내내는 것뿐이네. C 컴파일러가 `matrix[r][c]`를 저 공식으로 자동 변환해줄 뿐, 메모리 자체는 언제나 선형(linear)이라는 걸 여기서 직접 확인할 수 있음.

## 예제 4 — 포인터 연산 = 정수 덧셈 (Post-index로 포인터 순회)

**C 등가 코드**
```c
extern void go_print_int(int v);

int main(void) {
    int scores[5] = {95, 82, 67, 45, 78};
    int *p = scores;      // 배열 이름 = 첫 원소의 주소
    int sum = 0;

    for (int i = 0; i < 5; i++) {
        sum += *p;         // 포인터 역참조
        p++;                // 포인터를 "int 하나 크기(4바이트)"만큼 전진
    }

    go_print_int(sum);   // 367 (예제1과 동일한 결과!)
    return 0;
}
```

**ARM64 어셈블리 (Post-index 활용)**
```asm
    .text
    .global _main
    .extern _go_print_int

_main:
    stp     x29, x30, [sp, #-48]!
    mov     x29, sp

    mov     w0, #95
    str     w0, [sp, #16]
    mov     w0, #82
    str     w0, [sp, #20]
    mov     w0, #67
    str     w0, [sp, #24]
    mov     w0, #45
    str     w0, [sp, #28]
    mov     w0, #78
    str     w0, [sp, #32]

    add     x21, sp, #16              // int *p = scores;  (p = 배열 시작주소)
    mov     w19, #0                    // sum
    mov     w20, #5                    // 남은 원소 개수(카운터)

ptr_loop:
    cbz     w20, ptr_end

    ldr     w0, [x21], #4              // ★ *p 로드하고 나서 p += 4 (post-index, "역참조 후 전진"이 한 명령!)
    add     w19, w19, w0                // sum += *p

    sub     w20, w20, #1
    b       ptr_loop

ptr_end:
    mov     w0, w19
    bl      _go_print_int                // 367 — 예제1과 정확히 같은 결과!

    mov     w0, #0
    ldp     x29, x30, [sp], #48
    ret
```

**포인트 — 배열 인덱싱과 포인터 순회는 결국 같은 것**
- 예제 1: `base + i*4`를 **매번 새로 계산** (인덱스 방식)
- 예제 4: 포인터 자체를 **한 칸씩 전진**시키며 계산을 생략 (포인터 방식) — `[x21], #4`(post-index)가 "지금 주소에서 값을 읽고, 그다음 주소값을 4 증가"를 한 명령으로 처리

두 방식 모두 `sum = 367`로 **정확히 같은 결과**를 내는 걸 확인할 수 있는데, 이게 바로 C에서 `scores[i]`와 `*(scores + i)`가 완전히 동일한 코드로 컴파일되는 이유이기도 하네. "포인터 연산은 정수 덧셈일 뿐"이라는 명제가 여기서 증명되는 셈.

## 11주차 정리

| 개념 | 핵심 |
|---|---|
| 배열 인덱싱 | `base + index * element_size` (스케일드 오프셋 addressing mode) |
| `int` 배열 스케일 | `LSL #2` (또는 `SXTW #2`, 4바이트 단위) |
| 2차원 배열 | 메모리는 항상 1차원, `row*COLS+col` 공식으로 흉내낼 뿐 |
| 포인터 역참조+전진 | Post-index(`[Xn], #imm`)로 한 명령에 처리 가능 |
| 배열 vs 포인터 | 결국 같은 결과 — 컴파일러 관점에서도 동일 코드 생성 |
| CSEL 재등장 | 반복문 안에서 분기 예측이 불안정한 조건은 CSEL이 유리 |

---

12주차부터는 **구조체**로 넘어가서, 이번 주 배운 "고정 스케일(×4, ×8)"이 아니라 **필드마다 서로 다른 오프셋 상수**를 쓰는 법, 그리고 배열+구조체가 합쳐진 "구조체 배열"까지 다뤄볼 걸세. 진행해도 될까, 법우?
