
# CONST DATA SECTION

이거 정말 좋은 그림 소재구먼, 법우! 매크로 하나하나가 실제 Mach-O 세그먼트와 1:1로 대응되니, 이번엔 그림으로 한 장 딱 정리해보겠네.좋은 통찰이네, 법우! 매크로 10개가 정확히 Mach-O 세그먼트 두 곳(__TEXT/__DATA)에 나뉘어 들어가는 걸 한 장으로 그려보겠네.매크로 10개가 정확히 **두 세그먼트**로만 나뉘는구먼 — 놀랍지 않게도 1:1 매칭이 완벽하네.

## 짚어줄 만한 미묘한 부분 하나 — `CONST_DATA_SECTION`

이름은 "const"인데 왜 `__TEXT`가 아니라 `__DATA`에 들어가는지 의아할 수 있는데, 이유가 재밌네:

- `__TEXT`의 `__const`(읽기전용 상수)는 **컴파일 시점에 이미 최종 값이 확정**되는 것들(정수 배열, 룩업 테이블)이라 처음부터 읽기전용으로 둬도 안전함
- 반면 `CONST_DATA_SECTION`(`__DATA,__const`)은 **함수 포인터 테이블처럼 "주소값"을 담고 있는데, 그 주소가 dyld(동적 링커)가 라이브러리를 실제 메모리에 올린 뒤에야 확정**되네. 그래서 **프로그램 시작 시점엔 "쓰기 가능" 상태로 있다가, dyld가 재배치(relocation)를 다 끝낸 뒤에 `mprotect`로 읽기전용으로 잠가버리는** 방식이네
- 그래서 "논리적으로는 상수"지만 "물리적으로는 초기엔 변경 가능해야 하는" 이 특이한 성격 때문에 `__TEXT`가 아니라 `__DATA` 세그먼트에 위치하는 것이네

## 법우의 원래 질문 — heap/stack은 이 매크로 중 어디?

**정답: 이 10개 매크로 중 그 어느 것도 힙/스택을 다루지 않네.** 이유가 명확한데:

- 이 매크로들은 전부 **컴파일/링크 타임에 파일에 고정되는 섹션**(어셈블러가 오브젝트 파일을 만들 때 결정)
- 반면 **힙**은 런타임에 `malloc`(내부적으로 `brk`/`mmap` syscall)이 동적으로 늘려주는 영역, **스택**은 런타임에 `SP` 레지스터가 오르내리며 만드는 영역 — **둘 다 "실행 중"에 생기는 것**이지 바이너리 파일 안에 미리 박혀있는 섹션이 아니네

그래서 이전에 그려드린 전체 메모리 지도에서, **`__TEXT`+`__DATA` 세그먼트 = 정적(static) 영역(파일에서 그대로 로드)**, 그 위에 **힙/스택 = 동적(dynamic) 영역(런타임에 커널이 관리)**이라는 구도로 이해하면 딱 맞아떨어지네 — 이번 그림이 "정적 영역 확대도"이고, 지난번 그림이 "정적+동적 전체 지도"였던 셈이지.

---

좋은 시도인데, 절반은 맞고 절반은 다르네 법우. 정확히 짚어보겠네.

## 비슷한 점 — "한 번 정해지면 그 뒤로는 못 바꾼다"

**"처음엔 값이 확정 안 됐다가, 특정 시점 이후로 불변이 된다"**는 큰 그림은 정확히 같네. `readonly` 필드도 생성자 안에서만 값을 대입할 수 있고, 그 이후엔 컴파일러가 재대입을 막아주는 것처럼, `CONST_DATA_SECTION`도 "처음엔 쓰기 가능 → 특정 시점 이후 잠김"이라는 흐름은 동일하네.

## 다른 점 1 — "누가" 잠그는가

| | C# `readonly` | `CONST_DATA_SECTION` |
|---|---|---|
| 잠그는 주체 | **컴파일러(IL 검증기)** — 문법적으로 재대입을 막음 | **운영체제(mprotect)** — 물리적으로 그 메모리 페이지 자체를 하드웨어 레벨에서 쓰기 불가로 바꿈 |
| 위반 시 결과 | 컴파일 에러 (실행 전에 잡힘) | 세그멘테이션 폴트 (실행 중 크래시) |

즉 `readonly`는 "언어가 약속을 지켜주는" 소프트한 보호이고, `CONST_DATA_SECTION`은 **"메모리 자체가 물리적으로 못 쓰게 잠기는"** 훨씬 하드한 보호네. 언어와 상관없이(어셈블리로 직접 그 주소에 `str` 명령을 날려도) 무조건 크래시가 나네.

## 다른 점 2 — "언제, 몇 번" 초기화되는가

- **C# `readonly`**: 생성자가 호출될 **때마다**, 인스턴스(객체) **각각**의 필드에 값이 들어감 — 인스턴스 A와 B가 서로 다른 `readonly` 값을 가질 수 있음
- **`CONST_DATA_SECTION`**: 프로그램 **전체를 통틀어 딱 한 번**, dyld(동적 링커)가 **프로세스 시작 시(생성자 개념 자체가 없음, `main()`보다도 먼저)** 함수 포인터 주소들을 채워 넣고 잠가버림 — "인스턴스"라는 개념이 없는, **모듈/프로세스 단위의 전역 상수**

## 더 가까운 C# 비유를 찾자면

`readonly` 인스턴스 필드보다는, **`static readonly` 필드가 모듈 초기화자(module initializer)에서 한 번만 채워지는 것**에 훨씬 가깝네. 그리고 담기는 내용(함수 포인터 테이블)까지 감안하면, .NET 런타임이 내부적으로 관리하는 **가상함수 테이블(vtable/method table)**과도 비슷한 결의 개념이라 보면 되겠네 — JIT가 한 번 만들어놓고 그 뒤로는 아무도 안 건드리는 그 테이블 말일세.

**정리하면**: "한 번 초기화되고 그 뒤로 불변"이라는 **개념적 방향**은 정확히 짚었지만, `readonly`는 언어가 소스코드 레벨에서 지켜주는 약속이고, `CONST_DATA_SECTION`은 OS가 하드웨어 레벨에서 물리적으로 잠가버리는, **한 단계 더 낮고 더 강력한 보호**라고 이해하면 딱 맞겠네.

## 델리게이트 "선언" 자체는 아니네

```csharp
public delegate int DemoDelegate();
```

이건 **타입(청사진)을 선언하는 것**이지, 실제 메모리에 값(주소)이 들어있는 게 아니네. 비유하자면 C의 `typedef int (*FuncPtr)(void);`와 같은 급 — 이건 **"이런 모양의 함수 포인터"라는 틀만 정의**한 것이고, 실제 데이터는 하나도 안 생기네. 굳이 대응시키자면 이 선언은 컴파일러가 생성해주는 `Invoke` 메서드의 **코드**니까, 오히려 `__TEXT,__text`(실행 코드) 쪽에 더 가깝네.

## `CONST_DATA_SECTION`에 진짜 가까운 건 "함수 포인터를 담은 배열"

```csharp
// 이게 훨씬 더 가까운 비유일세
static readonly DemoDelegate[] OpTable = { MethodA, MethodB, MethodC };
```

**"여러 함수의 주소를 배열 형태로 모아놓고, 한 번 채워진 뒤로는 안 바뀐다"**는 이 구조가 실제로 `__DATA,__const`(8바이트 주소값들의 배열)와 개념적으로 맞아떨어지네 — 7주차에서 배웠던 **점프 테이블**(`ADR`+`LDR`+`BR`)이 바로 이 패턴의 순수 어셈블리 버전이었지.

## 그런데 여기서 결정적인 차이가 하나 남네

| | `static readonly DemoDelegate[]` | `CONST_DATA_SECTION` |
|---|---|---|
| 실체 | **힙에 할당된 객체 배열** (각 원소가 델리게이트 객체, GC가 관리) | **플랫한 raw 메모리 블록** (그냥 8바이트 정수값들의 나열) |
| 주소 안정성 | GC가 **압축(compaction)** 하면서 객체를 이리저리 옮길 수 있음(.NET GC 특성상) | dyld가 한 번 배치하면 **그 물리 주소가 프로세스 종료까지 절대 안 움직임** |
| 오버헤드 | 델리게이트 객체 하나하나가 타입정보, 대상 인스턴스 참조 등을 포함한 **꽤 무거운 객체** | 순수 포인터 값 하나(8바이트)만 존재, 아무 부가정보 없음 |

**정말로 딱 맞는 대응을 찾자면**, C# 9부터 나온 **네이티브 함수 포인터**(`delegate* unmanaged<...>`)를 `static readonly` 배열에 담은 경우가 제일 가깝네:

```csharp
static readonly unsafe delegate*<int>[] OpTable = { &MethodA, &MethodB, &MethodC };
```

이건 GC가 관리하는 객체가 아니라 **순수 주소값(포인터)만 담는 배열**이라, `__DATA,__const`의 "8바이트 quad 값들의 배열"이라는 물리적 실체와 정확히 같은 모양이 되네.

**정리하면**: "함수 주소들을 배열로 묶어서 나중에 다이내믹하게 찾아 쓴다"는 **아이디어의 방향**은 정확히 짚으셨지만, 일반 `delegate`는 관리형 힙 객체라 GC가 움직일 수 있는 반면, `CONST_DATA_SECTION`은 **한 번 고정되면 절대 안 움직이는 raw 메모리**라는 게 근본적인 차이일세 — 그래서 `unsafe delegate*` 쪽이 훨씬 더 순수한 대응이 되는 것이지.

## 법우가 짚은 흐름을 정확한 순서로 정리하면

**1단계 — "포인팅 할 함수 자체가 메모리에 로드"** (정확히 맞음)
- `MethodA`, `MethodB` 같은 실제 코드는 **`__TEXT,__text`**에 이미 파일 그대로 로드되어 있음 (11주차~까지 우리가 계속 짰던 그 코드!)
- 이건 컴파일 시점에 **상대 위치는 확정**돼 있지만, **절대 주소는 아직 모름** — 프로그램이 메모리 어디에 로드될지는 실행 시점에 OS가 정하니까(ASLR)

**2단계 — "긴가민가" 구간 (dyld의 재배치 작업 중)**
- `CONST_DATA_SECTION`(`__DATA,__const`)의 배열 슬롯들은 이 시점엔 **아직 빈 값(placeholder)**이거나 **쓰기 가능 상태로 열려있음**
- dyld가 "아, `MethodA`가 실제로 메모리 `0x1000A230`에 로드됐구나" 하고 확인한 뒤, 그 **실제 절대주소를 계산해서 이 슬롯에 채워 넣음** — 법우 표현대로 정말 "긴가민가" 상태에서 "기다!" 하고 확정되는 순간이네

**3단계 — "할당하고 읽기전용으로 잠그기"** (정확히 맞음)
- 모든 함수 포인터 슬롯이 다 채워지면, dyld가 그 메모리 페이지에 `mprotect(PROT_READ)`를 걸어서 **이제부터 쓰기 시도하면 무조건 크래시**나게 물리적으로 잠가버림
- 이 시점부터가 진짜 `readonly`가 되는 순간 — **`main()`이 실행되기도 전에** 이미 다 끝나있는 일이네

## 델리게이트 비유로 다시 한 줄 요약하면

```
[MethodA 코드 자체]        →  __TEXT,__text에 이미 존재 (컴파일타임에 확정)
        ↓ dyld가 로드 후 실제 주소 확인
[OpTable[0] = &MethodA]    →  __DATA,__const 슬롯에 "긴가민가" 채워짐
        ↓ 모든 재배치 완료
[mprotect(READ_ONLY)]      →  이제 진짜 불변, C#의 readonly 계약이 완성되는 순간
```

법우가 처음 "readonly 생성자 초기화"에서 시작해서, "델리게이트 배열"을 거쳐 지금 이 3단계 흐름까지 스스로 도달한 게 — 사실 이게 바로 **모든 실행파일 로더(dyld, ld.so 등)가 공통으로 하는 "지연 바인딩(lazy binding) 후 잠금"이라는 범용 패턴**이네. macOS든 Linux든, .NET이든 네이티브든, 다 이 그림 하나로 설명이 되는 것이지. 정말 제대로 감 잡았네, 법우! 하하하.
