# ARM64 예제 코드 — 9주차: 함수와 호출 규약 (AAPCS64)

> 드디어 8주차의 "복붙의 고통"을 해결할 도구가 등장하네. 지금까지는 `bl`로 **남이 만든**
> 브릿지 라이브러리(Rust/Go/.NET)만 호출했지만, 이번 주부터는 **우리가 직접 함수를 정의**하고,
> 그 함수도 똑같은 규약(AAPCS64)을 지키게 만드는 게 핵심이네.

---

## AAPCS64란 — 먼저 규약표부터

**AAPCS64**(ARM Architecture Procedure Call Standard, 64-bit)는 "함수를 어떻게 호출하고 어떻게 값을 주고받을지"에 대한 **약속**이네. 이 약속을 지켜야 Rust/Go/.NET 브릿지와도, 우리가 만든 함수끼리도 서로 안전하게 호출할 수 있음.

| 규칙 | 내용 |
|---|---|
| 정수/포인터 인자 | X0 → X1 → X2 → ... → X7 순서로 (최대 8개) |
| 부동소수점 인자 | V0 → V1 → ... → V7 순서로 (정수 인자와 별도 카운트) |
| 9번째 인자부터 | 스택에 쌓음 (이번 주는 안 다룸, 8개 이내로만 예제 구성) |
| 리턴값 | X0 (64비트 이하), 128비트 값은 X0+X1 쌍 |
| Caller-saved | X0~X18 — **호출하는 쪽이 필요하면 자기가 알아서 저장**. 함수는 이 레지스터를 마음대로 덮어써도 됨 |
| Callee-saved | X19~X28 — **함수(callee)가 이 레지스터를 쓰려면, 자기가 저장했다가 리턴 전에 복원**해야 함 |
| SP 정렬 | `BL`을 호출하는 시점에 SP는 **항상 16바이트 정렬** 상태여야 함 (안 지키면 크래시 가능) |
| FP(X29)/LR(X30) | 함수 진입 시 저장, 리턴 전 복원 (leaf function은 생략 가능) |

## 예제 1 — 첫 함수 정의: `grade_of` (8주차 복붙 해결!)

**C 등가 코드**
```c
extern int sys_print(const char* fmt);

int grade_and_print(int score) {   // 우리가 만드는 함수
    const char* msg;
    if      (score >= 90) msg = "등급: A\n";
    else if (score >= 80) msg = "등급: B\n";
    else if (score >= 70) msg = "등급: C\n";
    else if (score >= 60) msg = "등급: D\n";
    else                   msg = "등급: F (낙제)\n";

    sys_print(msg);
    return score >= 60;   // pass 여부 리턴
}

int main(void) {
    grade_and_print(95);
    grade_and_print(67);
    grade_and_print(45);
    return 0;
}
```

**ARM64 어셈블리**
```asm
    .data
    .align  3
grade_a: .asciz "등급: A\n"
grade_b: .asciz "등급: B\n"
grade_c: .asciz "등급: C\n"
grade_d: .asciz "등급: D\n"
grade_f: .asciz "등급: F (낙제)\n"

    .text
    .extern _sys_print

// ═══════════════ 함수 정의: int grade_and_print(int score) ═══════════════
    .align  2
grade_and_print:
    stp     x29, x30, [sp, #-32]!   // FP/LR 저장 + w19 보관 공간
    mov     x29, sp
    str     w19, [sp, #16]           // ★ w19(callee-saved)를 쓸 거라, 호출자의 값을 먼저 보존

    mov     w19, w0                  // score(인자, w0)를 callee-saved 레지스터로 옮겨둠
                                      // → 곧 bl _sys_print를 호출하면 w0가 덮어써지므로!

    cmp     w19, #90
    b.ge    ga_
    cmp     w19, #80
    b.ge    gb_
    cmp     w19, #70
    b.ge    gc_
    cmp     w19, #60
    b.ge    gd_
    b       gf_
ga_:
    adrp    x0, grade_a@PAGE
    add     x0, x0, grade_a@PAGEOFF
    b       do_print_
gb_:
    adrp    x0, grade_b@PAGE
    add     x0, x0, grade_b@PAGEOFF
    b       do_print_
gc_:
    adrp    x0, grade_c@PAGE
    add     x0, x0, grade_c@PAGEOFF
    b       do_print_
gd_:
    adrp    x0, grade_d@PAGE
    add     x0, x0, grade_d@PAGEOFF
    b       do_print_
gf_:
    adrp    x0, grade_f@PAGE
    add     x0, x0, grade_f@PAGEOFF
do_print_:
    bl      _sys_print                // x0 = 문자열 주소, Rust가 출력

    cmp     w19, #60
    cset    w0, ge                     // 리턴값: pass(1)/fail(0) → w0

    ldr     w19, [sp, #16]             // ★ 호출자의 w19 값 복원 (반드시!)
    ldp     x29, x30, [sp], #32
    ret                                 // 호출한 곳(main)으로 복귀

// ═══════════════ main ═══════════════
    .global _main
_main:
    stp     x29, x30, [sp, #-16]!
    mov     x29, sp

    mov     w0, #95
    bl      grade_and_print             // 8주차엔 이 자리에 15줄짜리 CMP체인이 통째로 있었지!

    mov     w0, #67
    bl      grade_and_print

    mov     w0, #45
    bl      grade_and_print

    mov     w0, #0
    ldp     x29, x30, [sp], #16
    ret
```

**포인트 — 8주차와 직접 비교해보게**
8주차 미니 프로젝트에서 학생 3명 처리에 **각각 약 20줄씩, 총 60줄 가까이 복붙**했었지. 이번엔 함수 하나(`grade_and_print`, 약 25줄)를 정의하고 **`main`에서는 3줄(`mov`+`bl`)씩만 반복**하면 끝이네. 학생이 30명이어도 함수 코드는 그대로고, `main`만 `mov w0, #점수; bl grade_and_print` 두 줄씩 30번 반복하면 됨. **이게 함수의 존재 이유**일세.

**포인트 — callee-saved 레지스터를 "직접" 저장/복원한 이유**
`grade_and_print` 함수는 내부적으로 `w19`를 씀. 그런데 `w19`는 **callee-saved**라서, 이 함수를 호출한 쪽(`main`이든 다른 함수든)이 `w19`에 뭔가 중요한 값을 담아뒀을 수도 있다는 전제가 깔려 있음. 그래서 함수 시작할 때 **`str w19, [...]`로 저장**해두고, 리턴 직전에 **`ldr w19, [...]`로 복원**해줘야, 호출자 입장에서 "내가 부른 함수가 w19 값을 안 건드렸다"고 믿을 수 있는 것이네. 이게 AAPCS64가 "callee-saved"라고 부르는 이유 — **저장의 책임이 callee(불려지는 쪽)에게 있다**는 뜻.

## 예제 2 — 여러 인자 함수 (X0~X7 순서 확인)

**C 등가 코드**
```c
// 가중평균: (a*wa + b*wb + c*wc) / (wa+wb+wc)
int weighted_avg(int a, int wa, int b, int wb, int c, int wc) {
    int weighted_sum = a*wa + b*wb + c*wc;
    int weight_total = wa + wb + wc;
    return weighted_sum / weight_total;
}

extern void go_print_int(int v);

int main(void) {
    int result = weighted_avg(90, 3, 80, 2, 70, 1);  // 중간고사*3 + 과제*2 + 출석*1
    go_print_int(result);
    return 0;
}
```

**ARM64 어셈블리**
```asm
    .text

// int weighted_avg(int a, int wa, int b, int wb, int c, int wc)
// 인자 순서 그대로 x0=a, x1=wa, x2=b, x3=wb, x4=c, x5=wc 에 자동으로 들어옴
    .align  2
weighted_avg:                        // leaf function (bl 없음) → 스택 프레임 불필요!
    mul     w6, w0, w1                // a*wa
    mul     w7, w2, w3                // b*wb
    add     w6, w6, w7                // + b*wb
    mul     w7, w4, w5                // c*wc
    add     w6, w6, w7                // weighted_sum 완성 (w6)

    add     w7, w1, w3                // wa+wb
    add     w7, w7, w5                // weight_total 완성 (w7)

    sdiv    w0, w6, w7                // 리턴값 = weighted_sum / weight_total
    ret

    .global _main
    .extern _go_print_int
_main:
    stp     x29, x30, [sp, #-16]!
    mov     x29, sp

    mov     w0, #90                   // a
    mov     w1, #3                    // wa
    mov     w2, #80                   // b
    mov     w3, #2                    // wb
    mov     w4, #70                   // c
    mov     w5, #1                    // wc
    bl      weighted_avg              // 인자 6개, X0~X5에 순서대로

    bl      _go_print_int             // weighted_avg의 리턴값(w0)이 그대로 다음 함수 인자로!

    mov     w0, #0
    ldp     x29, x30, [sp], #16
    ret
```

**포인트**
- `weighted_avg`는 내부에서 `bl`을 전혀 안 쓰는 **leaf function**이라 X29/X30 저장이 필요 없음 — "함수는 무조건 프롤로그/에필로그가 필요하다"는 오해를 깨는 예제
- `w6`, `w7`을 임시 계산용으로 자유롭게 씀 — **caller-saved(X0~X18) 레지스터는 함수가 저장 없이 마음껏 써도 됨** (호출한 쪽이 필요하면 자기가 알아서 지켰어야 함)
- `bl weighted_avg` 직후 `w0`에 리턴값이 있는 상태에서 곧바로 `bl _go_print_int`를 호출 — **리턴값이 이미 첫 번째 인자 자리(w0)에 있으니 별도로 옮길 필요가 없는** 편리한 우연(?)이 자주 발생함

## 예제 3 — Caller-saved 레지스터가 왜 위험한지 직접 확인

**의도적으로 틀린 코드 → 올바른 코드 비교**

**❌ 위험한 코드 (caller-saved를 안 지키면 생기는 버그)**
```asm
    mov     x0, #100
    mov     x9, #999           // x9는 caller-saved! 나중에 쓰려고 여기 담아둠 (위험한 패턴)
    bl      grade_and_print    // 이 함수 내부에서 x9를 자유롭게 덮어쓸 수 있음!
    // 여기서 x9가 999라고 믿으면 안 됨 — 값이 바뀌었을 수도 있음
```

**✅ 올바른 코드**
```asm
    mov     x0, #100
    mov     x19, #999           // callee-saved(x19)에 담으면 안전 (함수가 알아서 보존해줌)
    bl      grade_and_print
    // 여기서 x19는 반드시 999 — 규약상 보장됨
```

**포인트**
- X0~X18(caller-saved)은 **"내가 부르는 함수가 이 값을 마음대로 바꿀 수 있다"**는 전제하에 사용해야 함. 호출 너머로 값을 지키고 싶으면 **호출 전에 스스로 저장**하거나(스택 등) **애초에 callee-saved(X19~X28)를 쓰는 것**이 정답
- 반대로, X19~X28을 쓰는 함수는(예제1의 `grade_and_print`처럼) **자기가 그 레지스터를 건드리는 순간부터 저장/복원의 의무**를 지게 됨

## 예제 4 — SP 16바이트 정렬이 왜 중요한가

```asm
// ❌ 잘못된 예 (정렬 위반) — 시연용, 실제로 넣으면 크래시 가능성 있음
    sub     sp, sp, #4          // 4바이트만 내림 → SP가 16의 배수가 아니게 됨!
    bl      grade_and_print     // 이 시점에 SP가 정렬 안 되어 있으면 크래시 위험

// ✅ 올바른 예
    sub     sp, sp, #16         // 항상 16의 배수 단위로 조정
    bl      grade_and_print
    add     sp, sp, #16
```

**포인트**
- ARM64는 `LDP`/`STP`(레지스터 쌍 로드/스토어) 같은 명령이 **정렬된 메모리 접근을 전제**로 최적화되어 있고, macOS/Linux 둘 다 **`BL` 호출 시점의 SP 16바이트 정렬을 강제**하네 (특히 macOS는 이 위반에 엄격해서 바로 크래시가 나는 경우가 흔함)
- 그래서 지금까지 모든 예제에서 스택 프레임 크기를 항상 16, 32, 48처럼 **16의 배수**로 잡았던 것 — 우연이 아니라 규약이었던 것이네

## 9주차 정리

| 개념 | 핵심 규칙 |
|---|---|
| 인자 전달 | X0~X7(정수), V0~V7(부동소수점), 순서대로 채움 |
| 리턴값 | X0 (필요시 X0+X1) |
| Caller-saved | X0~X18 — 함수가 마음대로 덮어써도 됨 (지키고 싶으면 호출자 책임) |
| Callee-saved | X19~X28 — 쓰려면 함수가 저장/복원 의무 |
| Leaf function | 내부에 `bl`이 없으면 FP/LR 저장 생략 가능 (예제2) |
| SP 정렬 | `bl` 호출 시점에 항상 16바이트 정렬 |
