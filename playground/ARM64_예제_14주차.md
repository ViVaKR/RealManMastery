# ARM64 예제 코드 — 14주차: 시스템 콜 & C 라이브러리 연동

> 원안대로 진행하되, 한 가지는 먼저 짚고 가야겠네: **이번 주 "직접 시스템 콜" 예제는 Linux AArch64 기준**이네.
> macOS(Darwin)는 raw syscall 번호·ABI를 애플이 공개 안정 API로 취급하지 않고(버전마다 바뀔 수 있음), `SVC` 직접 호출 대신
> **libSystem을 거치도록 강제**하는 게 공식 방침이라, 우리가 1주차 이후 줄곧 `_main`+브릿지 라이브러리 경로로 온 게 바로 이 이유였던 것이네.
> 다수의 학습자가 Linux ARM64를 쓸 거란 말씀대로, 이번 주는 **"Linux에서는 이렇게도 할 수 있다"**를 제대로 보여드리겠네.

## Linux AArch64 시스템 콜 규약

| 규칙 | 내용 |
|---|---|
| 시스템콜 번호 | **X8** 레지스터에 지정 |
| 인자 | X0 → X1 → X2 → X3 → X4 → X5 (최대 6개, AAPCS64 함수 인자 규약과 유사하지만 레지스터 개수 제한이 다름) |
| 호출 | `SVC #0` |
| 리턴값 | X0 (음수면 보통 `-errno`) |

**자주 쓰는 syscall 번호 (AArch64 Linux 기준)**

| 이름 | 번호 | 용도 |
|---|---|---|
| `openat` | 56 | 파일 열기 (AArch64엔 `open`이 없고 `openat`만 있음!) |
| `close` | 57 | 파일 닫기 |
| `read` | 63 | 읽기 |
| `write` | 64 | 쓰기 |
| `exit` | 93 | 프로세스 종료 |

**⚠️ 주의 — `open`이 아니라 `openat`인 이유**: 32비트 시절 레거시 syscall(`open`, `unlink` 등)들이 AArch64에서는 아예 제거되고 `*at` 계열(`openat`, `unlinkat`)로 통일됐네. `AT_FDCWD`(-100)를 디렉토리 fd 자리에 넣으면 "현재 작업 디렉토리 기준"이라는 뜻이 되어 옛날 `open`과 동일하게 동작하네.

## 예제 1 — 파일 쓰기 (openat + write + close)

**C 등가 코드**
```c
#include <fcntl.h>
#include <unistd.h>

int main(void) {
    int fd = open("output.txt", O_CREAT | O_WRONLY | O_TRUNC, 0644);
    write(fd, "ARM64 파일 입출력 테스트\n", 29);
    close(fd);
    return 0;
}
```

**ARM64 어셈블리 (Linux, GNU ELF 문법)**
```asm
    .data
filename:
    .asciz  "output.txt"
content:
    .ascii  "ARM64 파일 입출력 테스트\n"
content_end:
    .equ    CONTENT_LEN, content_end - content    // 컴파일 타임에 길이 자동 계산!

    .text
    .global main

main:
    stp     x29, x30, [sp, #-16]!
    mov     x29, sp

    // ── openat(AT_FDCWD, filename, O_CREAT|O_WRONLY|O_TRUNC, 0644) ──
    mov     x0, #-100                    // AT_FDCWD
    adrp    x1, filename                  // Linux ELF 문법: @PAGE/@PAGEOFF 대신 :lo12: 사용 (3주차에서 예고했던 부분)
    add     x1, x1, :lo12:filename
    mov     x2, #0x241                    // O_CREAT(0x40) | O_WRONLY(0x1) | O_TRUNC(0x200)
    mov     x3, #0644
    mov     x8, #56                        // openat
    svc     #0
    mov     x19, x0                         // fd를 callee-saved에 보관 (9주차 규칙 그대로 적용!)

    // ── write(fd, content, CONTENT_LEN) ──
    mov     x0, x19
    adrp    x1, content
    add     x1, x1, :lo12:content
    mov     x2, #CONTENT_LEN
    mov     x8, #64                          // write
    svc     #0

    // ── close(fd) ──
    mov     x0, x19
    mov     x8, #57                           // close
    svc     #0

    mov     w0, #0
    ldp     x29, x30, [sp], #16
    ret
```

**포인트**
- `.equ CONTENT_LEN, content_end - content`: 문자열 길이를 **직접 세지 않고 어셈블러가 계산**하도록 함 — 한글(UTF-8, 멀티바이트)이 섞이면 손으로 세기 번거로우니 이 관용구가 특히 유용
- `mov x19, x0`으로 `fd`를 보관하는 것도 결국 9주차에서 배운 **"함수 호출(여기선 syscall) 사이에 값을 지키려면 callee-saved에"**의 연장선. syscall도 `write`, `close`처럼 **여러 번 걸쳐 값을 참조**해야 하면 똑같은 원리가 적용되네
- 이 예제는 `main`(C 런타임 진입점)을 쓰면서도 **내부에서 raw syscall을 자유롭게 섞어 쓸 수 있다**는 걸 보여줌 — "syscall이냐 `main`이냐"는 양자택일이 아니라, `main`은 그냥 진입 방식일 뿐이고 그 안에서 뭘 하든(라이브러리 호출이든 syscall이든) 우리 마음이라는 것

## 예제 2 — 파일 읽기 & 화면 출력 (read + write(1, ...))

**C 등가 코드**
```c
#include <fcntl.h>
#include <unistd.h>

int main(void) {
    char buf[128];
    int fd = open("output.txt", O_RDONLY);
    long n = read(fd, buf, sizeof(buf));
    close(fd);
    write(1, buf, n);   // stdout에 그대로 출력
    return 0;
}
```

**ARM64 어셈블리**
```asm
    .data
filename:
    .asciz  "output.txt"

    .text
    .global main

main:
    stp     x29, x30, [sp, #-160]!    // FP/LR(16) + buf[128] → 정렬 위해 160
    mov     x29, sp

    // ── openat(AT_FDCWD, filename, O_RDONLY) ──
    mov     x0, #-100
    adrp    x1, filename
    add     x1, x1, :lo12:filename
    mov     x2, #0                      // O_RDONLY = 0
    mov     x8, #56
    svc     #0
    mov     x19, x0                      // fd

    // ── read(fd, buf, 128) ──
    mov     x0, x19
    add     x1, sp, #16                  // buf 시작주소 (3주차: 스택 = 지역변수)
    mov     x2, #128
    mov     x8, #63                        // read
    svc     #0
    mov     x20, x0                         // 실제로 읽은 바이트 수 (callee-saved에 보관)

    // ── close(fd) ──
    mov     x0, x19
    mov     x8, #57
    svc     #0

    // ── write(1, buf, n) : 읽은 내용을 그대로 화면에 출력 ──
    mov     x0, #1                          // stdout
    add     x1, sp, #16
    mov     x2, x20                          // 읽은 만큼만 출력 (버퍼 전체가 아니라!)
    mov     x8, #64
    svc     #0

    mov     w0, #0
    ldp     x29, x30, [sp], #160
    ret
```

**포인트**
- `read`의 리턴값(`x0`)은 **실제로 읽은 바이트 수**(요청한 128보다 작을 수 있음) — 이걸 `write`에 그대로 넘겨야, 버퍼의 쓰레기값까지 출력되는 실수를 막을 수 있음
- 파일 디스크립터(`fd`)와 읽은 바이트 수(`n`)를 **서로 다른 callee-saved 레지스터(x19, x20)**에 나눠 보관 — 4주차에서 예고했던 "여러 값을 여러 함수/syscall 호출 너머로 보존"하는 실전 사례

## 예제 3 — 진짜 `printf` 직접 호출하기 (C 라이브러리 연동)

지금까지는 우리가 만든 브릿지 라이브러리(`go_print_int`, `sys_print`)만 썼는데, 사실 **표준 C 라이브러리의 `printf`도 그냥 평범한 함수라 AAPCS64 규약만 지키면 직접 호출 가능**하네.

**C 등가 코드**
```c
#include <stdio.h>

int main(void) {
    int score = 95;
    printf("점수: %d\n", score);
    return 0;
}
```

**ARM64 어셈블리 — Linux (glibc)**
```asm
    .data
fmt: .asciz "점수: %d\n"

    .text
    .global main
    .extern printf

main:
    stp     x29, x30, [sp, #-16]!
    mov     x29, sp

    adrp    x0, fmt
    add     x0, x0, :lo12:fmt      // 첫 인자(x0) = 포맷 문자열 주소
    mov     w1, #95                 // 두 번째 인자(가변인자, %d 자리) = w1
    bl      printf

    mov     w0, #0
    ldp     x29, x30, [sp], #16
    ret
```

**ARM64 어셈블리 — macOS (libSystem, 우리가 써온 `_main` 관례 그대로)**
```asm
    .data
fmt: .asciz "점수: %d\n"

    .text
    .global _main
    .extern _printf

_main:
    stp     x29, x30, [sp, #-16]!
    mov     x29, sp

    adrp    x0, fmt@PAGE
    add     x0, x0, fmt@PAGEOFF
    mov     w1, #95
    bl      _printf

    mov     w0, #0
    ldp     x29, x30, [sp], #16
    ret
```

**포인트 — 가변인자(variadic) 함수인데 왜 특별한 처리가 없나**
x86-64(SysV ABI)에서는 가변인자 함수를 호출할 때 **"부동소수점 인자를 몇 개 썼는지"를 `AL` 레지스터에 표시**해야 하는 특이한 규칙이 있는데, **ARM64(AAPCS64)에는 그런 규칙이 아예 없음** — 그냥 평소처럼 X0~X7/V0~V7에 인자를 순서대로 채우기만 하면 `printf`가 알아서 포맷 문자열(`%d`, `%s`...)을 보고 몇 개를 읽을지 스스로 판단하네. 이게 ARM64 호출 규약이 x86-64보다 단순한 지점 중 하나일세.

**포인트 — 이제 3가지 출력 수단을 다 갖추게 됐네**
1. **Raw syscall** (`write`) — 가장 저수준, OS와 직접 대화
2. **libc `printf`** — 표준 C 라이브러리, 포맷팅 편의성
3. **브릿지 라이브러리** (`sys_print`, `go_print_int` 등) — 법우가 직접 만든 Rust/Go/.NET 생태계 활용

세 가지 모두 **"AAPCS64 규약을 지키는 함수(또는 syscall)를 `bl`/`svc`로 호출한다"**는 동일한 원리 위에 있다는 걸 이번 주 전체가 증명해준 셈이네.

## 14주차 정리

| 방법 | 호출 명령 | 특징 |
|---|---|---|
| Raw syscall | `SVC #0` (X8=번호) | OS 커널과 직접 통신, 플랫폼별 번호/ABI가 다름 (Linux만 안정적으로 문서화됨) |
| libc 함수 (`printf` 등) | `BL` | AAPCS64 규약 그대로, 가변인자도 특별한 처리 불필요 |
| 커스텀 브릿지 (Rust/Go/.NET) | `BL` | libc 함수와 호출 방식이 완전히 동일 (전부 AAPCS64 준수 함수이므로) |

| Linux 문법 | macOS 문법 | 차이 |
|---|---|---|
| `adrp x1, sym` / `add x1, x1, :lo12:sym` | `adrp x1, sym@PAGE` / `add x1, x1, sym@PAGEOFF` | 3주차에서 예고했던 것이 이번 주 실전 사용까지 이어짐 |
| `.global main` | `.global _main` | Mach-O 언더스코어 컨벤션 |
