# ARM64 예제 코드 — 7주차: switch문 (CMP 체인 vs 점프 테이블)

> 6주차에서 "if/while/for는 CMP+B.cond+B의 조합"이라 정리했는데,
> **switch도 결국 이 조합의 확장판**이네. 다만 case가 많고 값이 연속적일 때는
> 컴파일러가 완전히 다른 전략(점프 테이블)을 쓰기 시작하지 — 이번 주는 그 갈림길을 보는 게 핵심이네.

---

## 예제 1 — CMP 체인 방식 (case가 적거나 값이 듬성듬성할 때)

**C 등가 코드**
```c
extern void go_print_int(int v);

int main(void) {
    int day = 3;
    int result;

    switch (day) {
        case 1: result = 10; break;
        case 2: result = 20; break;
        case 3: result = 30; break;
        default: result = -1; break;
    }

    go_print_int(result);   // 30
    return 0;
}
```

**ARM64 어셈블리**
```asm
    .text
    .global _main
    .extern _go_print_int

_main:
    stp     x29, x30, [sp, #-16]!
    mov     x29, sp

    mov     w19, #3              // day

    cmp     w19, #1
    b.eq    case_1
    cmp     w19, #2
    b.eq    case_2
    cmp     w19, #3
    b.eq    case_3
    b       case_default          // 어느 것도 매치 안 되면 default로

case_1:
    mov     w20, #10
    b       switch_end
case_2:
    mov     w20, #20
    b       switch_end
case_3:
    mov     w20, #30
    b       switch_end
case_default:
    mov     w20, #-1

switch_end:
    mov     w0, w20
    bl      _go_print_int          // 30 출력

    mov     w0, #0
    ldp     x29, x30, [sp], #16
    ret
```

**포인트**
- 이건 사실 **`if-else if-else if-...-else` 체인과 완전히 동일한 구조**네 — 6주차 예제 1이 case 하나짜리로 반복된 것뿐
- case 값이 3개뿐이라 컴파일러도 보통 이 방식(선형 비교)을 씀. **case 개수가 적을 때(대략 4~5개 미만)나, 값이 0,1,2,100,1000처럼 듬성듬성(sparse)할 때** 이 방식이 선택됨
- 단점: case가 N개면 최악의 경우 **비교를 N번** 해야 함 (O(N))

## 예제 2 — 점프 테이블 방식 (case 값이 촘촘하고 많을 때)

**C 등가 코드**
```c
extern void go_print_int(int v);

int main(void) {
    int op = 2;   // 0,1,2,3 중 하나 — 연속된 값!
    int result;

    switch (op) {
        case 0: result = 100; break;
        case 1: result = 200; break;
        case 2: result = 300; break;
        case 3: result = 400; break;
        default: result = -1; break;
    }

    go_print_int(result);   // 300
    return 0;
}
```

**ARM64 어셈블리 (ADR + LDR + BR 패턴)**
```asm
    .text
    .global _main
    .extern _go_print_int

_main:
    stp     x29, x30, [sp, #-16]!
    mov     x29, sp

    mov     w19, #2              // op

    // ── 범위 체크 (0~3 벗어나면 default로) ──
    cmp     w19, #3
    b.hi    case_default          // unsigned 비교: op가 0~3 범위 밖(음수 포함)이면 default

    // ── 점프 테이블 계산: base + table[op] ──
    adr     x1, jump_table         // 테이블 시작 주소
    ldr     w2, [x1, w19, uxtw #2] // w2 = jump_table[op] (각 항목 4바이트, op*4 오프셋)
    add     x1, x1, w2, sxtw       // 테이블에 저장된 "상대 오프셋"을 더해 실제 목적지 주소 완성
    br      x1                    // 계산된 주소로 무조건 점프!

case_0:
    mov     w20, #100
    b       switch_end
case_1:
    mov     w20, #200
    b       switch_end
case_2:
    mov     w20, #300
    b       switch_end
case_3:
    mov     w20, #400
    b       switch_end
case_default:
    mov     w20, #-1
    b       switch_end

    .align  2
jump_table:
    .word   case_0 - jump_table    // 테이블엔 절대주소가 아니라 "테이블 시작 기준 상대 오프셋"을 저장 (PIC-safe)
    .word   case_1 - jump_table
    .word   case_2 - jump_table
    .word   case_3 - jump_table

switch_end:
    mov     w0, w20
    bl      _go_print_int          // 300 출력

    mov     w0, #0
    ldp     x29, x30, [sp], #16
    ret
```

**포인트 — 이게 왜 빠른가**
- case가 몇 개든 **비교는 딱 1번(범위 체크)** 뿐이고, 나머지는 **테이블 인덱싱 + 계산된 점프(BR)**로 바로 목적지에 도착 (O(1))
- `BR`은 `B`(무조건분기)와 달리 **런타임에 계산된 주소로 점프**하는 명령 — 컴파일 시점에 목적지가 고정된 `B`/`B.cond`와 근본적으로 다른 부류의 명령이네
- 테이블에 **절대주소가 아니라 상대 오프셋**(`case_0 - jump_table`)을 저장하는 이유: 프로그램이 메모리 어디에 로드되든(ASLR 등) 안전하게 동작하는 **위치 독립 코드(PIC, Position-Independent Code)**를 만들기 위함. macOS/최신 Linux 실행파일은 기본적으로 PIC로 빌드되니 이 패턴이 표준이네
- **왜 case 값이 "연속적"이어야 하나**: 테이블은 인덱스로 바로 오프셋 계산(`op*4`)을 하는 구조라, `0,1,2,3`처럼 촘촘해야 테이블 크기가 낭비 없이 딱 맞음. `0, 1000, 2000`처럼 듬성듬성하면 테이블이 쓸데없이 커져서 오히려 예제 1(CMP 체인) 방식이 더 유리해짐

## 두 방식 직접 비교해보기 — objdump로 확인

7주차 커리큘럼 원안에 있던 대로, 실제로 C 컴파일러가 어떤 기준으로 두 방식을 선택하는지 직접 확인해볼 수 있네:

```bash
# case 3개짜리 switch (예제1과 유사한 C)와
# case 8개 이상 연속값 switch (예제2와 유사한 C)를 각각 컴파일해서 비교
clang -O2 -S -o - switch_sparse.c   | grep -A5 "cmp\|b\."
clang -O2 -S -o - switch_dense.c    | grep -A5 "adrp\|jump"
```

case 개수가 적으면 `cmp`/`b.eq` 체인이, 개수가 많고 연속적이면 점프 테이블(`adrp` + 오프셋 로드 + `br`)이 나오는 걸 직접 눈으로 확인해보면 이번 주 내용이 훨씬 체감될 걸세.

## 7주차 정리 — 6주차와 어떻게 이어지는가

| 구분 | 6주차 (if/while/for) | 7주차 예제1 (CMP 체인) | 7주차 예제2 (점프테이블) |
|---|---|---|---|
| 핵심 명령 | `CMP` + `B.cond` + `B` | `CMP` + `B.cond` + `B` (동일! 반복만 늘어남) | `CMP`(범위체크 1회) + **`BR`**(계산된 점프) |
| 시간복잡도 | - | O(N) — case 개수만큼 비교 | O(1) — 인덱스로 즉시 도달 |
| 목적지 결정 시점 | 컴파일 타임 (고정) | 컴파일 타임 (고정) | **런타임** (테이블에서 계산) |
| 적합한 상황 | - | case 적음 / 값 듬성듬성 | case 많음 / 값 연속적 |

결국 7주차의 결론은: **"switch는 새로운 문법이 아니라, if-chain의 확장(예제1)이거나, 완전히 새로운 도구인 BR(계산된 분기)을 쓰는 최적화(예제2)냐의 갈림길"**이라는 것이네. 6주차의 `B`/`B.cond`만으로는 점프 테이블을 설명할 수 없고, **`BR`이라는 세 번째 분기 명령**이 처음 등장했다는 점도 놓치지 말고 챙겨두게.
