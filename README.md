# RealManMastery

>- Modern ARM64 Assembly Mastery from bare hands to bare-metal. Pure architecture without bloat.
>- 맨몸으로 시작해 쌩 하드웨어 베어메탈까지 타격하는 진짜 상남자의 ARM64 정복기 (12시간 통합 코스)


## 기본사항 (Apple Silicon 환경)

- 심볼 접두사 (Underline) : Apple Mach-O 포맷 규칙에 따라 호출할 함수 이름 앞에 반드시 언더바(_) 를 붙임.
- ARM64는 함수 호출시 파라미터를 레지스터 (x0 ~ x7)로 넘김
- 주석 : `//` 또는 `/* ... */` 를 사용
- 컴파일 및 빌드 팁 : 대문자 `.S` 확장자로 파일을 만들면 Clang 전처리기를 통해 C 언어 매크로도 섞어 쓸 수 있음.
``` clang -arch arm64 main.S -o my_program```

- 지시자 `.set` 정체 
    - .set 은 `이 이름을 이 값으로 정의` 하겠다 라는 의미
    - 다른 어셈블리 에서 `.equ` 나 `=` 기호와 똑 같은 역할 을 함
    ``` .set MY_VAL, 10``` : MY_VAL 을 10으로 설정 (C언어의 #define MY_VAL 10)
- `#pragma once` : 컴파일러에게, 이 파일 딱 한 번만 읽으라는 의미

### Clang/GAS 어셈블리 매크로

- ARM64 다목적 비트 연산 매크로

```c
/* 
   [설명] 특정 레지스터의 비트를 제어하는 매크로
   - dest: 무조건 지정해야 함 (:req)
   - src: 안 적으면 dest 레지스터 자체를 가리킴 (=dest)
   - bit: 안 적으면 기본값 0번 비트 제어 (=0)
*/
.macro BIT_CONTROL dest:req, src=\dest, bit=0
    and \dest, \src, #(1 << \bit)
.endm

// --- 활용법 ---
BIT_CONTROL x0          // 결과: and x0, x0, #(1 << 0)
BIT_CONTROL x0, x1, 4   // 결과: and x0, x1, #(1 << 4)
```

- 문자열 결합(\.)과 가변 인자 (:vararg)

### 포인터 인증(PAC, Pointer Authentication)

- 예시

```asm
_secure_function:
    pacibsp                     // [프롤로그] B-키를 이용해 현재 X30(링크 레지스터) 서명인증
    stp x29, x30, [sp, #-16]!
    
    // ... 함수 본문 ...
    
    ldp x29, x30, [sp], #16
    autibsp                     // [에필로그] X30의 서명이 올바른지 검증 (위조 시 크래시)
    ret

```

— **이 패턴 자체는 매우 보편적이지만, 손으로 직접 쓰기보다는 컴파일러가 자동으로 넣어주는 경우가 훨씬 많습니다.** 그리고 부작용도 몇 가지 실질적으로 존재합니다.


## 이게 뭘 하는 코드인가 — ROP/JOP 공격 방어

`pacibsp`/`autibsp`는 **Pointer Authentication (PAC)**, ARMv8.3-A부터 도입된 기능입니다.

```
pacibsp   → LR(x30)에 "서명"을 심음 (SP 값을 컨텍스트로, B키 사용)
autibsp   → 함수 나가기 직전, 그 서명이 위조되지 않았는지 검증
```

목적은 **ROP(Return-Oriented Programming) 공격 차단**입니다. 스택 버퍼 오버플로우 등으로 공격자가 `x30`(리턴 주소)을 조작해서 원하는 곳으로 점프시키려 해도, 서명이 안 맞으면 `ret` 실행 시 즉시 크래시가 나서 익스플로잇이 실패합니다.

## 보편성 — 실제로는 "이미 다들 쓰고 있는" 수준

이게 특수한 실험적 기법이 아니라 **주요 플랫폼의 기본값에 가깝습니다**:

| 플랫폼 | 상태 |
|---|---|
| **Apple arm64e (M1/M2/M3 등)** | 시스템 바이너리 대부분에 이미 강제 적용됨 |
| **Android (Pixel 등 최신 기기)** | `-mbranch-protection=pac-ret`로 컴파일러가 기본 삽입 |
| **Linux (ARM64)** | 커널 자체가 PAC 지원, 유저스페이스도 `-mbranch-protection` 옵션으로 활성화 가능 |

다만 실전에서는 사람이 어셈블리에 직접 `pacibsp`를 타이핑하는 경우는 거의 없고, **clang/gcc에 컴파일 플래그 하나만 주면 컴파일러가 함수 프롤로그/에필로그에 자동으로 끼워 넣습니다**:

```bash
clang -mbranch-protection=pac-ret ...
```

즉 지금 보신 코드는 "컴파일러가 내부적으로 하는 일을 사람이 손으로 재현해본 것"이라, 저 두 줄을 직접 타이핑할 일은 거의 없습니다.

## 부작용 — 몇 가지 실질적인 것들이 있습니다

### 1. PAC 미지원 CPU에서도 안전하게 동작 (다행인 부분)
`pacibsp`/`autibsp`는 ARM의 "hint 인코딩 공간"을 씀 — PAC를 지원 안 하는 구형 ARMv8.0 CPU에서는 그냥 **NOP으로 무시**됩니다. 그래서 하위 호환성 자체는 문제없습니다.

### 2. 성능 오버헤드 (미미하지만 존재)
매 함수 호출마다 서명/검증 연산이 추가되므로, **함수 호출이 극도로 빈번한 핫패스**에서는 측정 가능한 수준의 오버헤드가 생깁니다 (보통 1~수 % 수준으로 보고되지만 워크로드마다 다름).

### 3. Leaf 함수 최적화와의 충돌
`bl`을 전혀 안 쓰는 leaf 함수(오늘 우리가 처음 봤던 진짜 최소 스택 함수 같은 것)는 원래 x30을 스택에 저장할 필요조차 없는데, PAC를 켜면 이런 함수도 `pacibsp`/`autibsp`를 넣게 되는 경우가 있어 최소한의 오버헤드가 "leaf인데도" 붙습니다.

### 4. 디버깅이 살짝 더 헷갈려짐
서명된 포인터는 **상위 비트에 서명값이 섞여 들어가서**, `lldb`에서 raw로 `x30`을 찍어보면 정상적인 주소값처럼 안 보이고 이상한 큰 수로 보일 수 있습니다. (`register read lr`을 하면 실제로 서명이 섞인 값이 나오는 경우가 있어, `strip pac bits` 처리를 지원하는 최신 디버거 버전이 필요합니다.)

### 5. 서로 다른 키/설정으로 컴파일된 모듈 간 링크 이슈
PAC는 A키/B키(그리고 IA/IB/DA/DB 등 용도별로 여러 키)가 있는데, **컴파일 시 브랜치 보호 설정이 다른 오브젝트 파일들을 섞어 링크**하면 (예: 한쪽은 PAC 활성화, 한쪽은 비활성화) 크래시 없이 조용히 섞이거나, 혹은 링커가 경고를 내는 경우가 있어서 빌드 시스템 전체의 일관성이 중요해집니다.

### 6. "만능 방패"는 아님 — 특정 공격만 막습니다

- PAC는 **리턴 주소 위조**에 특화된 방어입니다. 스택의 다른 데이터(지역 변수, 버퍼 자체)를 조작하는 공격 자체를 막는 건 아니고, 그 데이터로 프로그램 흐름을 바꾸려는 시도 중 "리턴 주소를 노리는 경로"만 차단합니다.

- 힙 오버플로우, use-after-free 등은 PAC의 보호 범위 밖입니다.

## 정리

| 항목 | 평가 |
|---|---|
| 보편성 | 매우 높음 — Apple/Android/Linux ARM64 모두 사실상 표준으로 채택 중 |
| 손코딩 필요성 | 낮음 — 컴파일러 플래그(`-mbranch-protection`) 하나로 자동 삽입 |
| 성능 부작용 | 미미하지만 존재 (특히 leaf 함수/핫패스) |
| 디버깅 부작용 | 있음 — 서명된 x30 값이 raw로 보이면 헷갈림 |
| 빌드 일관성 부작용 | 있음 — 혼합 컴파일 설정 시 링크 문제 가능 |
| 보안 범위 | 리턴주소 위조 방어에 특화, 만능 방어책 아님 |

즉, 이건 손으로 쓸 코드가 아님, 아이폰/안드로이드 폰의 거의 모든 프로세스 안에서 조용히 돌아가고 있는 보안 기법
